2 版本外显 每个文档页面必须在其元数据区域以结构化（机器可优先读）和自然语言（人类可读）两种形式，明确声明：产品/项目名称、文档对应的软件版本号（遵循SemVer）、该版本的发布日期、该版本的生命周期状态（如当前稳定版、维护中、已启用、EOS）、（可选）文档版本自身的版本号。所有版本差异必须使用表格进行条目化描述，禁止使用模糊散文。 版本元数据展示，不使用JS动态渲染：
在页面固定位置（参考 NV 放顶部导航栏或 H1 下方）展示产品名、版本号、发布日期、生命周期状态，位置全站统一。

生命周期状态标签：
稳定版、维护中、已弃用、EOS 用不同颜色的标签组件区分，与失效状态原则的警告色保持一致的色彩语义体系，不能各自定义颜色

版本差异表格样式（可选）：
版本对比内容必须用表格呈现，表格列头（版本号、差异项、说明）样式清晰，设计上禁止用列表或段落替代表格来呈现版本差异		 版本元数据结构化字段：
CMS 中为每个页面增加强制填写的结构化字段：product-name、software-version（SemVer 格式校验）、release-date、lifecycle-status，发布时校验必填，缺失则阻断。

元数据机器可读输出：
版本信息同步写入页面 <head> 的 <meta> 标签和 JSON-LD，如 softwareVersion、datePublished、releaseNotes 字段，供大模型直接读取，不依赖解析页面正文；

SemVer 格式校验：
CMS 在版本号字段录入时强制校验 SemVer 格式（X.Y.Z），拒绝模糊写法如"最新版"、"V2"；

版本元数据在大纲接口中透传：
页面大纲接口返回结果中包含版本元数据字段，大模型消费接口时可直接获取版本上下文，无需进入页面解析。		 实测诊断
3 失效状态显化 失效状态显性化。版本、上线、废弃、灰度、兼容边界明确写明，AI自动过滤失效内容；已废弃章节在页顶展示弃用提示，并链接代替文档。
a.功能/接口失效
任何已弃用、将下线、或对特定环境无效的功能、API端点、配置参数、必须在描述它的最靠近的标题下方使用显著的警告块进行标记。该警告必须说明：弃用/失效的时间点（或版本）、影响范围、以及代替方案（链接到新文档）。
b.文档失效
对于已停止维护的文档版本或章节，必须在页面顶部（H1上方）展示一个清晰的提示框，说明“此文档适用于已停止维护的[产品名]vX.Y”，并提供一个指向最新版本推荐文档的醒目链接。		 警告块组件规范：
功能/接口失效的警告块需要有统一的视觉样式（颜色、图标、边框），与普通提示框、信息框明确区分，视觉权重足够高，用户不会忽略；

页顶文档失效提示框：
位置固定在 H1 上方，样式与正文完全隔离（如全宽背景色条），包含失效说明文本和指向新文档的醒目链接，不能被页面其他内容淹没。		 失效状态元数据字段：
CMS 中为每个页面和内容块增加结构化字段，包括 status（active / deprecated / sunset）、deprecated-since（版本或时间）、replacement-url（替代文档链接），与内容分离管理，不依赖人工在正文中手写；

失效内容的机器可读标注：
废弃警告块加 data-status="deprecated"、data-since="vX.Y"、data-replacement="url" 属性，大模型抓取时可直接识别该内容块的有效性，自动过滤或降权失效内容；

页顶提示框自动渲染：
当页面 status 字段为 deprecated 时，由模板自动在 H1 上方注入提示框，不依赖内容侧手动添加，避免遗漏；

失效内容在大纲接口中标注：
上文已有页面大纲接口，此处需在接口中为每个内容块带上 status 字段，供大模型在消费大纲时直接过滤失效章节，无需进入页面逐一判断。		 —
4 元数据丰富化
阳狮团队已识别		 元数据字段填写：每篇文档在 Markdown frontmatter 中填写 doc_id、version、date_modified、applicable_devices、parent_topic 等字段，这是两轨交付和 JSON-LD 自动生成的数据来源
文档摘要补充：每篇文档 H1 下方补充 60-120 字的摘要块，说明"这篇文档是关于什么产品、面向什么读者、解决什么问题"，严格控制在 150 字符以内		 面包屑导航样式：
文本路径完整可见（文档中心 / Ascend C / 算子开发 / 算子开发入门），禁止折叠或省略中间层级。

摘要块样式（可选）：
H1 下方摘要区有独立的视觉容器，字色略浅于正文，与正文内容有明确间距区分。		 JSON-LD 自动生成：
构建管道从 Markdown frontmatter 自动生成 TechArticle + BreadcrumbList 的 JSON-LD，注入页面 <head>，不依赖人工编写。

/docs/{doc_id}/metadata.json 端点：
每篇文档提供独立的元数据 JSON 接口，输出 doc_id、version、date_modified、applicable_devices、breadcrumb、prev/next/parent_topic 等字段，供 Agent 直接消费。

prev/next/parent_topic 写入 meta：
页面 <head> 中输出 <link rel="prev">、<link rel="next">、<link rel="up"> 标签，关系链从文档目录结构自动推导。

面包屑文本在 SSR 首屏直出：
面包屑路径作为真实文本节点输出到 HTML，不依赖 JS 动态生成，确保爬虫可抓取完整路径层级。		 实测诊断

5 图文图意 架构图、流程图、时序图、界面截图关键信息、核心结论采用文本介绍，图片做辅助展示。
a.代替文本
每一张图（<img>）必须提供非空的alt属性。alt文本应简洁描述图片的内容和功能
b.禁止“见上图/下图”
正文中禁止出现“见上图/下图”等仅依赖视觉位置进行引用的语句。图片引用必须将图片中的关键信息用文字复述一遍
c.复杂图表转写
对于包含复杂逻辑的图表，必须在图片下方提供一个“图表内容转写”段落，用文字完整描述图表所表达的全部关键信息。
d.替代格式优先
对于流程图、时序图、架构图，优先使用Mermaid 等文本可渲染的图表格式代替不可读的PNG/JPG图片
e.装饰图片
纯装饰性的图标、分割线图片等，应使用CSS背景图或标记 alt=“”（空字符串）		 图表格式规范：
所有流程图、时序图、架构图，在交付给研发时优先提供 Mermaid 源码，而不是导出 PNG/JPG。如果 Mermaid 表达不了，提供 SVG 源文件。

图片排版预留 figcaption 位：
每张图片下方在设计稿中预留 figcaption 注释区域，作为内容转写的展示位，纳入排版规范，不能设计成没有这个位置的图文布局。

复制链接按钮设计：
在 figcaption 段落旁设计"复制链接"按钮，以及点击后的 toast 轻提示样式（文案如"已复制链接"，持续约 2 秒后消失）。这个按钮需要出现在每个 figcaption 区域。

使用装饰性图片识别：
在设计交付标注中，明确标出哪些图片是装饰性的（图标、分割线等），告知研发这些元素标记 aria-hidden="true" 或使用 CSS 背景图实现，不需要 alt 文字。		 HTML 结构实现：
每张图片用 <figure> + <figcaption> 包裹，<img> 上填写设计侧提供的 alt、title、data-llm-transcription 三个字段。每个 <figure> 需要有唯一 id 作为锚点。

复制链接按钮功能：
figcaption 旁实现"复制链接"按钮，点击后将当前图片的锚点 URL 写入剪贴板，同时触发 toast 提示"已复制链接"，2秒后自动消失。每个 <figure> 需要有唯一的 id 作为锚点。

Mermaid / SVG 渲染支持：
研发侧引入 Mermaid 渲染库，支持在文档内容中直接嵌入 Mermaid 代码块并渲染为可交互图表。SVG 图表直接内联到 HTML 中，而不是作为 <img> 引用，保证文本可提取。

Chunk 切片管道：
在内容切片逻辑中，将每张图片的 alt + figcaption 文字 + 图片前后的正文段落拼接为一个连续文本块，作为该图片的语义 chunk 供向量化索引使用。装饰性图片（aria-hidden="true" 或 role="presentation"）跳过，不参与切片。

装饰性图片标记：
纯装饰性元素（图标、分割线）改用 CSS background-image 实现；若必须使用 <img>，标记 alt="" 加 role="presentation" 或 aria-hidden="true"，确保不被内容提取管道处理。		 实测诊断
6 图片热区 对于包含可点击区域（ImageMap，既带有<map>和<area>标签的图片），图片下方必须提供给一个完整的、无序列表样式的链接清淡，清单中列出所有热区对应的跳转目标。每个清淡项必须包含：热区所代表的描述性文字，以及完整的跳转URL。禁止在清单中使用“区域1”、“链接2”等无意义的描述。 热区语义文案交付：
设计交付时，针对每一个 <area> 热区，同步提供：
a.描述性文字：热区代表的阶段名、文档名或功能名，禁止用"区域1""链接2"等无意义文字
b.alt 文案：填入 <area alt>，一句话描述该热区的跳转目标
c.title 文案：补充热区的上下文说明

热区链接清单设计：
在图片下方的 figcaption 区域内，预留热区链接清单的展示位，样式为无序列表，每项包含描述性文字和跳转目标，与 figcaption 图意转写并排或紧随其后。		 <area> 标签补全：
每个 <area> 必须填写 alt 和 title，href 必须为绝对 URL，禁止使用相对路径。

<nav> 文本链接清单实现：
在每个带有 <map> 的图片下方，用 <nav> 包裹一个无序列表，覆盖全部热区目标，<a> 标签内必须有描述性锚文本，href 为绝对 URL。与 figcaption 图意转写组合展示。

绝对 URL 转换：
构建管道中自动将 <area href> 和 <nav> 内 <a href> 的相对路径转换为绝对 URL，确保机器可直接引用和跳转。

Chunk 切片管道：
在上一轮切片逻辑基础上，针对热区图片额外提取 <nav> 内的链接清单文本，与 data-llm-transcription、figcaption、周围正文拼接为一个完整 chunk。		 实测诊断
7 链接语义 内容引用超链接采用描述性、可见文字显性标注跳转目标，实现AI可访问性和搜索索引性。
a.描述性锚文本
超链接的可点击文本必须能够在不依赖上下文的情况下，独立描述链接的目标内容或操作。禁止使用“点击这里”、“更多”、“链接”作为锚文本。
b.站外来源标注
对于指向其他域名的链接，应在锚文本旁添加显式标识，如[外部]或图标+目标域名
c.内联上下文
链接应嵌入在具有上下文的句子中，而不是孤立地列出
d.用途说明
对于下载链接、API参考链接等，可在链接后附带括号说明文件类型、大小或用途。		 锚文本写作规范：
建立链接文案规范，纳入内容审核流程，同时覆盖正文链接和热区链接：
a.锚文本必须能独立描述跳转目标，脱离上下文也能理解
b.禁止使用"点击这里""更多""链接""查看详情"作为锚文本
c.下载链接、API 链接在锚文本后附带括号说明文件类型、大小、用途
d.热区的 area alt / area title 文案同步提供，禁止使用"区域1""链接2"等无意义文字		 描述性锚文本实现：
正文 <a> 标签内必须有描述性文字，href 为绝对 URL。下载链接和 API 链接在锚文本后附带 <span> 说明用途，不影响链接本身的语义.

站外链接自动标识：
构建管道中检测 <a href> 是否跨域，跨域链接自动注入外部标识和 rel="noopener noreferrer" 属性，同时添加 data-external="true" 供切片管道识别.

热区 <area> 标签补全：
每个 <area> 填写描述性 alt 和 title，href 为绝对 URL。

Chunk 切片管道：
在已有切片逻辑基础上，针对链接语义追加提取规则：
a.提取每个 <a> 的锚文本 + href，拼接为"锚文本 → 绝对URL"格式，纳入所在段落的 chunk;
b.站外链接（data-external="true"）在 chunk 中标注来源域名;
c.热区链接从 figcaption 内的 <a> 提取，格式与正文链接一致;
d.裸 URL（无锚文本的 <a>）标记为低质量，降低索引权重。		 实测诊断
8 代码语义 代码示例格式清晰，提供完整可运行示例和预期输出。
a.独立可运行
代码示例应尽可能自包含，用户可以复制后直接运行
b.语言标注
每个代码块必须标注编程语言（如'"python）
c.注释清晰
关键行应包含注释，解释其作用
d.预期输出
对于执行类代码，应在代码块后提供“预期输出”块
e.格式分离
代码行号应由前端CSS或代码高亮库生成，严禁在代码文本中手动写入行号
f.区块语义
代码块应使用<pre><code>语义标签包裹
g.元信息
代码块上方（可选单推荐）显示该代码的文件名、适用语言和场景。		 定义代码块组件规范：
设计代码块组件，包含以下固定区域，纳入设计系统组件库：
a.顶部元信息栏：显示文件名、语言类型、适用场景，如 hello_world.cu | C++ | 基础bb.编译场景
c.代码区：行号由 CSS 渲染，不出现在可选中的文本中
d.底部预期输出块：执行类代码必须配套，样式与代码块区分（如不同背景色）
右上角复制按钮

预期输出块样式设计：
预期输出块与代码块视觉上明确区分，标题固定为"预期输出"，不使用"输出结果""运行结果"等变体，纳入格式规范。

元信息文案交付：
内容交付时，每个代码块同步提供：
a.文件名（如有）
b.语言类型
c.适用场景描述（一句话）
d.预期输出内容		 <pre><code> 语义结构实现：
所有代码块使用 <pre><code> 包裹，<code> 上标注 language-xxx 类名，禁止使用 highlighttable 表格布局。

行号 CSS 渲染，禁止写入文本节点：
行号通过 CSS counter 实现，不写入 <code> 文本内容，确保复制代码时不包含行号，切片管道拿到的是纯净代码文本；

HTML 实体解码：
切片管道入模前，将代码文本中的 HTML 实体还原为可读字符。

弃用 highlighttable 布局：
将现有使用 highlighttable 表格承载代码的结构全部迁移为 <pre><code> 结构。构建管道中加入检测，发现 highlighttable class 时阻断发布。

Chunk 切片管道追加规则：
在已有切片逻辑基础上，针对代码块追加：
a.提取 <code class="language-xxx"> 的语言类型作为 chunk 元数据
b.提取 .code-meta 内的文件名和场景描述，拼接到代码 chunk 头部
c.代码文本入模前执行 HTML 实体解码
d.code-output 块与对应代码块绑定为同一 chunk，不拆分
e.行号（::before 伪元素内容）不参与文本提取		 实测诊断
9 表格语义 表格中的符号需要替换为文本。
a.符号替换；
表格单元格中禁止使用仅靠形状表达含义的符号，如✅、❌、-、N/A等，所有状态必须使用完整的文字表达，如 是/否、支持/不支持
b.结构化标题
表格必须使用<caption>标签提供表格标题/摘要。列名称必须使用<th>标签 ；
c.作用域 <th>标签应尽可能指定 scope="col"或scope="row"		 符号替换规范：
建立表格内容写作规范，明确禁止使用仅靠形状表达含义的符号，所有状态必须用完整文字表达，纳入内容审核流程。

表格标题文案交付：
每张表格交付时同步提供 <caption> 文案，格式为"表N 描述性标题"，如"表1 Ascend C Add算子设计规格"，禁止使用"表格1""数据表"等无意义文字。

复杂表格结构标注：
复杂规格表（如含 I/O 子表、合并单元格、多级表头）在设计交付标注中明确：
a.哪些单元格是表头（需用 <th>），哪些是数据（用 <td>）
b.表头的作用域方向（scope="col" 或 scope="row"）
c.接口列表区域标注为独立列表结构，不拆成伪数据行		 表格完整语义结构实现：
所有表格使用完整语义结构，<caption> 写入表格标题，<thead> 包裹 <th>，<th> 指定 scope，<tbody> 包裹数据行。

复杂规格表 I/O 子表实现：
I/O 子表的 name / shape / data type / format 列必须使用 <th> 表头，禁止用样式伪装成表头的 <td>。行级表头使用 scope="row"。

Chunk 切片管道追加规则：
在已有切片逻辑基础上，针对表格追加：
a.<caption> 内容作为表格 chunk 的标题元数据，每行 chunk 均携带
b.<th scope="col"> 内容作为列名前缀，拼接到每个数据单元格
c.<th scope="row"> 内容作为行名前缀，拼接到该行所有数据单元格
d.接口列表（<ul>）与所属表格绑定为同一 chunk，不拆分
e.优先使用 Markdown 副本入库，HTML 表格作为降级来源		 实测诊断
10 安全警示语义 Note、注意、警告等安全警示提示正文在页面上完整展示，不折叠、不同tooltip藏字。
a.完整可见；
所有安全警示、注意事项、提示信息的内容必须完全在页面上展示，禁止使用折叠块、点击展开、鼠标悬停Tooltip、模态框等需要用户交互才能看到完整的内容的方式
b.文字前缀：
警示信息必须使用文字前缀明确表示其类型，如：**注意**、**警告**、**危险**。禁止仅使用图标来传递类型信息
c.结构化
建议为不同类型的安全警示定义固定的CSS类。		 警示块完整展示：
所有 Note/注意/警告内容必须直接渲染在页面上，禁止折叠、tooltip、模态框等交互形式，设计稿不出现任何需要点击才能看到警示内容的方案。

文字前缀必须可见：
警示类型必须用文字（"注意："、"警告："、"危险："）标注，图标只能作为辅助装饰，不能作为唯一的类型标识。

不同警示级别的视觉区分：
Note、注意、警告、危险用不同颜色的容器组件区分，颜色语义全站统一（如黄色=注意、红色=危险），与失效状态、生命周期状态的色彩体系保持一致		 data-admonition-type 属性标注：
每个警示块容器加 data-admonition-type="note|warning|tip|danger"，大模型可直接识别警示级别，不依赖解析图标或颜色；

文字前缀写入 DOM：
警示类型文字（"注意："、"警告："）必须作为真实文本节点输出到 HTML，禁止通过 CSS 伪元素 ::before 或图片生成，确保爬虫和大模型能直接读取；

嵌套层级保留：
步骤列表 <ol><li> 内嵌的警示块，DOM 结构中必须保持嵌套关系，禁止渲染时扁平化输出，确保大模型能识别"这条警告属于第几步"		 实测诊断
11 隐藏语义 避免折叠、隐藏或采用交互形式内容。
a.避免交互内容
核心文档内容应该以静态HTML/Markdown的形式存在。应避免使用依赖Java Script才能显示内容的交互式组件（Tab标签页、折叠/手风琴块、轮播图、动态加载）
b.Tab全量可见
如果必须使用Tab页签页，则必须提供一种无需点击即可访问所有Tab内容的方法
c.折叠默认展开
如果必须使用折叠组件（如<details>）,其open属性必须默认为true。关键步骤和说明禁止放在折叠区内。
d.折叠标题可读
折叠组件的标题（<summary>）必须包含有语义的文本		 避免隐藏：
如果必须用 Tab，设计上需要提供"展开全部"或页面内所有 Tab 内容垂直排列的备用布局，不能仅依赖点击切换，确保所有内容无交互即可看到。

折叠组件默认展开：
折叠块的设计默认状态为展开，折叠是用户主动收起的操作，而非默认隐藏内容的手段。

禁止核心内容进折叠：
设计规范中明确，关键步骤、警示信息、验证区块禁止放入折叠组件，折叠只用于附录、扩展说明等非核心内容。		 禁止 display:none 隐藏内容：
非激活 Tab 面板和折叠内容禁止用 display:none 或 visibility:hidden 隐藏，改用 visibility 配合 position 或其他不影响 DOM 可读性的方式处理视觉层叠，确保爬虫遍历到所有内容节点。

<details> 强制 open 属性：
所有折叠组件在 SSR 输出时默认带 open 属性，用户可手动收起，但初始 HTML 中内容必须完整存在。

<summary> 必须含语义文本：
折叠标题禁止只放图标或空节点，文本内容必须能独立描述折叠区的主题。

Tab 面板全量输出到 HTML：
所有 Tab 面板内容在 SSR 首屏 HTML 中完整输出，不依赖 JS 动态注入非激活面板内容，确保爬虫一次抓取即可获得所有面板文本。		 实测诊断
12 FAQ结构化 任何以问题/答案对（Q&A）形式呈现的内容，必须使用明确的视觉标记（如问：/答：前缀）和语义标记（如Schema.org 的Question/Answer类型），通常通过JSON-LD实现），将FAQ内容与普通叙述文本区分开。FAQ区块应有一个包裹容器（如 < div itemtype=“https://schema.org/FAQPage">)。 Q&A 视觉容器组件：
FAQ 区块需要有独立的视觉容器样式，与普通段落明确区分，问题行和答案行在字重、缩进或颜色上有差异，让用户一眼识别这是 Q&A 结构；

问/答前缀标记规范：
统一"问："/"答："或"Q："/"A："的字体样式和颜色，形成全站一致的视觉语言。		 FAQ 容器语义标签：
最外层包裹 <div itemscope itemtype="https://schema.org/FAQPage">，每个 Q&A 对用 <div itemscope itemtype="https://schema.org/Question"> 包裹，问题文本加 itemprop="name"，答案区块加 itemprop="acceptedAnswer"，这是大模型和搜索引擎识别 FAQ 结构的基础；

JSON-LD 同步输出：
在页面 <head> 中同步输出 FAQ 的 JSON-LD，与页面 Microdata 标注保持一致，两者都有可以互为兜底；

CMS 提供 FAQ 专属内容块类型：
编辑器中提供独立的 FAQ 组件，而非让内容侧在普通文本里手写"问："/"答："，确保语义标签由组件自动生成，不依赖人工添加。		 —
