链接语义

链接语义指锚文本、目标 URL 与链接意图对模型是否可读。站内相对链接、占位符「LINK」、全站导航噪声、以及图片热区中的裸 href，都会影响知识库中链接是否可理解、可检索、可引用。

部分可抓
核心问题
  • 正文 <a> 多数可解析，但占位符锚文本（如 HelloWorld 页「请参考 LINK」）使目标语义劣化入库
  • 图片热区链接无文本表达，模型无法感知跳转目标；全页约 282 个全局导航链接稀释正文链接权重
  • 面包屑 / 上下篇等 IA 链接在 HTML 中存在，但未标准化进 chunk 元数据，跨页关系难以召回

测试问题

读取 HelloWorld（CANN 9.0.0），完整样例代码在哪个仓库？再读 什么是 Ascend C，成长地图里的阶段入口链接能检索到吗？

结论：链接语义劣化或未入库

部分链接能进知识库，但关键跳转语义不可用。用户问「HelloWorld 样例仓库地址」「环境准备文档在哪」时，要么得到无意义锚文本「LINK」，要么根本没有热区链接 chunk——链接 URL 可能存在，语义对人类不可核对、对 RAG 不可检索。

1. 占位符链接 → 语义劣化

HelloWorld 等页出现「完整样例请参考 LINK」类表述：href 指向 GitCode 仓库，但锚文本不提供目标描述。入库后 chunk 中仅出现「LINK」——模型无法推断这是 hello_world 样例仓库。

<a href="https://gitcode.com/cann/ascendc-samples/tree/master/hello_world">LINK</a>

2. 热区链接 → 未入库（链接维度）

成长地图等热区图的 area href 不属于正文 <a>，默认转文本管道完全丢失。详见 图片热区。即使解析 HTML，裸文件名（如 atlas_ascendc_map_10_0003.html）也缺少「环境准备」等可读标签。

3. 全站导航噪声 → 正文链接稀释

渲染页 HTML 含约 282 个 o-link 全局导航（社区菜单、页脚、侧栏等）。默认整页抓取时，这些链接与正文链接混在同一上下文，稀释正文链接的语义权重，干扰 RAG 对文档内关键引用的识别。

4. IA 元数据链接 → 未标准化入库

面包屑、上一篇 / 下一篇、版本切换等链接在 HTML 中存在，但通常未作为结构化元数据写入 chunk。用户问「Ascend C 入门上一篇是什么」「当前文档版本」时，知识库缺少标准化字段可召回。

改进目标

让每条进入知识库的链接都携带可读的锚文本与明确目标——用户检索「样例仓库」「环境准备文档」「上一篇主题」时能召回正确 URL 与意图。热区链接须文本冗余，导航噪声须在机器层剥离。

改进措施

一、内容侧：链接文本化（P0，治本）

核心原则：链接意图先行入库——模型读到的文字应能回答「链到哪里、为什么链」。详见 亲和原则 · 链接语义。

做法入库效果
1 锚文本必须描述性，禁止「LINK」「点击这里」（L-01） chunk 可直接回答「样例在 hello_world 仓库」
2 站外链接保留完整 href，标注 external（L-02） 外部仓库 URL 可核对、可引用
3 站内链接机器层转绝对 URL（L-03） 相对路径不歧义，可跨页召回
4 热区 area 冗余为文本链接列表（L-04） 成长地图阶段入口可检索（见 图片热区）
5 链接附 title 或上下文说明（L-05） 增强向量检索与 LLM 引用准确性

机器层 Markdown 输出要点

完整样例请参考 [hello_world 完整样例（GitCode 仓库）](https://gitcode.com/cann/ascendc-samples/tree/master/hello_world)

二、架构侧：双轨交付 + 噪声剥离

双轨交付——人类层保留完整站点导航，机器层只保留正文区链接与元数据：

HTML 源（doc_center） │ ├──► 人类层：全站导航 + 热区 + 交互 UI（体验不变） │ └──► 机器层：正文 MD / JSON + llms.txt └── 剥离 ~282 项全局导航噪声 └── 描述性锚文本 + 绝对 URL └── breadcrumb / prev-next 写入元数据字段

RAG 只消费机器层；链接语义在发布环节规范化，而非检索时从噪声 HTML 中猜测。
