模块 02 · 当前问题 · 交付格式

交付格式

交付格式决定大模型抓取时读到的是纯净正文，还是 Nuxt SPA 壳层与全站导航噪声。 本页界定机器可选载体层级，以「什么是 Ascend C」实测 .md / .html 两种 URL，并量化渲染页噪声与全站壳层对入库的影响。

核心问题
  • 双轨缺失：人类阅读走 /document/detail/ 渲染页（单页 ~200KB+），机器层缺乏稳定、低噪声的并行 Markdown 出口；默认爬虫落在渲染页，全站导航与壳层稀释正文，RAG 入库信噪比差。
  • .md 名实不符：.md URL 仍走 Nuxt SPA，非纯 Markdown 交付；同页实测 MD 管线出现 [object Object]、锚文本丢失——扩展名不能作为「模型友好」判断依据。
  • 渲染页均非最优：无论 .md 还是 .html，热区等问题均未解决；/doc_center/source/ 源 HTML（4–11 KB）才是当前最佳可用载体，但入口未在机器层显式声明。

测试问题

同一篇「什么是 Ascend C」，机器层应通过哪条 URL、哪种载体读到完整正文、低噪声、可预测的文本？.md 扩展名是否等于 Markdown 文件？

载体层级

机器抓取社区文档时，理论上存在四层载体；实测主要针对最下两层渲染页。

改进目标

人类层保留现有渲染页体验；机器层通过同源双发获得纯净 MD / JSON——体积极小、噪声剥离、抓取结果可预测。RAG 与 Agent 只消费机器层，不再默认剥 224KB 渲染页壳层。

改进措施

一、双轨交付架构（P0）

结论：同源双发（Single Source, Dual Output）——不牺牲人类体验，同时为模型提供纯净消费层。

内容生产（HTML 源 /doc_center/source/） │ ├──► 人类阅读层：品牌化 HTML + 交互 UI（document/detail） │ └──► 模型消费层：MD / JSON + llms.txt 索引 └──► RAG 向量库 / Agent Tool Calling
方案优势劣势
只给 MD模型友好、Token 高效失去热区、Tab、品牌视觉
只给 HTML人类体验完整282 个导航链接污染上下文
双轨交付各取所长，同源维护需建设转换管道
  • 内容源 — /doc_center/source/ 干净 HTML，4–11 KB / 页
  • 人类出口 — 现有 document/detail 站点
  • 模型出口 — MD / JSON API / llms.txt（见 机器入口 · 解决方案）

二、格式优先级（P0）

场景推荐格式说明
RAG 入库MD + Front Matter切片友好，元数据可过滤
Agent 调用JSON API含 title、breadcrumb、code_blocks[]
人类阅读现有 HTML 站点保留交互与视觉
发现索引llms.txt声明机器友好 URL（见 机器入口）

三、转换管道（P0–P1）

以 /doc_center/source/ 为输入，自动执行：

  1. 剥离导航壳层、脚本、样式
  2. 图片热区 → 文本链接列表
  3. 注意提示 → MD 引用块
  4. Tab / 折叠 → 扁平 H3 展开
  5. 代码块 → 标注语言 + 文件名，去除行号
  6. 注入 YAML Front Matter（见 元数据 · 解决方案）
步骤输入输出
源提取doc_center/source HTML纯净 DOM
噪声剥离导航、脚本、样式正文 + 元数据
组件转换note / tab / imagemap / codeMD 等价结构
入库MD + 元数据向量库 / JSON API

四、与语义维度的边界

交付格式解决载体与噪声；正文内语义损失（热区、Tab、图意等）见 图片图意、Tab 等语义页——双轨交付提供干净载体，语义页规则在转换管道中落地。
