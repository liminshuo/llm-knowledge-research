页级元数据未结构化 语义未结构化

页级元数据指每篇文档的身份信息：CANN 版本、章节路径、文档编号、适用芯片——人看 URL 和标题能知道，入库后却没有可检索字段。 以 什么是 Ascend C 为例：9.0 / 8.5 / 9.1-beta 正文几乎相同、只有 URL 和标题版本串不同——不写 version 就会混召。

核心问题
  • 同一篇文档多版本并存（9.0 / 8.5 / 9.1-beta），入库不写 version 时检索新旧版混在一起
  • 章节路径挤在 <title> 一长串里，未拆成 breadcrumb——同名「环境准备」分不清教程线
  • 文档编号、适用芯片页面上有，未写入 chunk——引用只能贴 URL，难以唯一对应某一版某一页

问题实测

测试问题

我在 Ascend C 文档里看到 环境准备（CANN 9.0.0） 这篇——怎么知道它对应 CANN 9.0 还是 8.5？算入门教程还是安装文档？引用时有没有固定的文档编号？

结论：页面有身份、库里没标签

人看页面能知道「这是 9.0 版、入门教程第一章」；RAG 读 chunk 只能看到正文段落。版本、章节路径、文档编号散落在 URL 和 <title> 里，入库时未提取为独立字段——检索只能靠全文相似度，不能按版本筛、不能消歧同名章节、不能稳定引用。

解决方案

改进目标

每篇文档、每个正文切片入库时，带上能搜、能筛的身份标签——让 RAG 可以「只要 9.0 版」「只要入门教程线」「只要 Atlas A2 适用」，引用也能稳定对应到唯一 doc_id。

改进措施

  • 必要version：标明 CANN 版本，检索默认过滤到目标版，避免 8.5 / 9.0 混召；
  • 必要doc_id + source_url：稳定文档编号与双轨 URL，引用可唯一回溯；
  • 必要breadcrumb：把 title 里的章节路径拆成数组，消歧同名「环境准备」等章节；
  • 可选applicable_devices、keywords：按芯片型号、关键词精准过滤；
  • 可选prev / next：上下篇关系，支持按阅读顺序推理（详见 跨页关系）。

字段一览见 亲和原则 · IA 元数据字段。核心原则：页面上已有的身份信息，入库时必须变成字段。
