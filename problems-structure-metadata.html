页级元数据未结构化 语义未结构化

页级元数据指每篇文档的身份信息：CANN 版本、章节路径、文档编号、适用芯片——人看 URL 和标题能知道，入库后却没有可检索字段。 以 什么是 Ascend C 为例：9.0 / 8.5 / 9.1-beta 正文几乎相同、只有 URL 和标题版本串不同——不写 version 就会混召。

3. 问题洞察

大模型的回答与页面对照指向三点结论：

  • 页面有身份、库里没标签：人看 URL / 标题能知 9.0 版与章节位置，RAG chunk 只有正文——version、breadcrumb、doc_id 均未字段化。
  • 多版本混召：9.0 / 8.5 / 9.1-beta 正文几乎相同，不写 version 时检索新旧版混在一起。
  • 引用难唯一：文档编号、适用芯片页面上有，未写入 chunk——引用只能贴 URL，难以唯一对应某一版某一页。

探测详见 hiascend-metadata-probe.md。

根因分析

页级元数据未结构化的核心原因是：version / breadcrumb / doc_id 未字段化、Front Matter 缺失、chunk 无身份标签。

1. version 未字段化

版本号藏在 URL 与 <title> 里，入库不写 version——RAG 无法默认过滤 900，8.5 / 9.0 混召。

修改建议

页头展示 version 徽章，Front Matter 强制写入 version（详见 版本外显）。

2. breadcrumb 未拆分

章节路径挤在 <title> 一长串里——同名「环境准备」分不清教程线。

修改建议

渲染页展示面包屑，机器层写入 breadcrumb 数组。

3. doc_id 未携带

URL 文件名可当编号，但 chunk 无 doc_id——引用只能贴链接，无法稳定回溯。

修改建议

Front Matter 写入 doc_id + source_url，脚注可唯一对应文档。

4. 适用属性未入库

适用芯片等信息散落在正文，无 applicable_devices 等字段——无法按硬件过滤。

修改建议

页头展示适用芯片标签，入库写入 applicable_devices（字段模板见 页级元数据）。
