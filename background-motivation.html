研究概览

本研究聚焦昇腾社区 Ascend C 官方文档 如何进入大模型 RAG / 知识库。

人类阅读注重体验与效率优先。页面设计针对人类阅读习惯，利用视觉层级引导、图片热区、Tab 容器及品牌化布局，服务于速览、跳转、内容切换及代码复用等高频需求。

知识库入库要求语义完整与噪声剥离优先。入库规范针对知识检索场景，利用正文、图意、热区链接、代码与表格结构、IA 元数据的准确转写，服务于完整入库、可检索、可引用及跨页推理等核心需求，远不止正文段落。

同一套源文档需同时回答两个问题：人读得顺，与 机器读得全——后者是本研究的主线。

核心命题 RAG / 知识库尽量完整收录昇腾官方文档的文档语义。

研究范围

整体范围是昇腾官方文档 Ascend C 算子开发。 本研究主要聚焦下列五个典型页面——它们承载不同的组件类型与语义载体，覆盖了后续语义维度中的主要研究对象。

语义维度

昇腾官方文档的语义不限于正文段落，还广泛分布于图片、热区、链接、交互组件、代码、表格、提示框、页面元数据及版本信息等多层载体。默认抓取 .html 或 .md 渲染页面时，大量语义或因无法进入 RAG 而丢失，或被噪声稀释。

  • 语义完全丢失：知识库中无对应 chunk，如：图片无 alt 文本、热区跳转未被提取；
  • 语义劣化入库：文本已入库，但结构或类型被破坏，如：代码携带行号、链接被转为纯文本「LINK」；
  • 语义未结构化：页面上信息存在，但未转化为可检索的元数据，如：面包屑、版本号、设备型号。

1. 图片语义 语义完全丢失

常规抓取：图意仅存在于图片像素中，文档未提供文字等价物。由于默认处理管道不具备图像识别能力，因此无法产生可检索的正文。

抓取 HTML 源码：虽能读取 <img> 标签，但图意仍无法入库，还需：

  • 必要alt：在图片标签上补充图片说明，如「Ascend C 编译流程」，而非「zh-cn_image_xxx.png」等无意义文件名；
  • 必要data-llm-transcription：补充图片内容转写，将图中的节点、层级、箭头关系等均转为正文描述；
  • 可选figcaption：补充图注，如「图1：xxx」形式的说明段落；
  • 可选title：在图片标签上补充可提示的说明；
  • 可选使用可读取、可编辑的源文件（如 Mermaid 图源）替代纯图片。

以抓取 什么是 Ascend C（CANN 9.0.0） 为例，正文区的 6 张说明图对于向量检索和 LLM 引用而言，等同于空白。具体实测结果参见 问题论证 · 图片图意。

2. 图片热区 语义完全丢失

图片热区在默认抓取及默认 RAG 管道下，属于「语义完全丢失」类型。即便在专门解析 HTML 时能提取到裸 href，仍缺乏可检索的链接语义。因此，除补充上文所述的图片语义字段外，热区还需额外补充：

  • 必要nav：补充文本链接列表，覆盖全部热区目标；
  • 必要area alt / area title：补充热区标签。当前多数热区无标签，仅有坐标与裸 href；
  • 必要描述性锚文本：补充 <a> 标签内的文字内容。当前缺少阶段名/文档名，仅存文件名；
  • 必要绝对 URL：<a href> / <area href> 的属性值须为完整 URL。当前为相对路径，难以被机器直接引用或跳转。

以 什么是 Ascend C（CANN 9.0.0） 页面的「成长地图」为例：单图含 14 个热区入口（环境准备、HelloWorld 等），对向量检索和 LLM 引用而言形同空白链接。实测参见 问题论证 · 图片热区。

3. 链接语义 语义劣化入库

占位符链接在默认抓取及默认 RAG 管道下，属于「语义劣化入库」类型：href 虽能入库，但锚文本未提供目标描述，chunk 中仅出现「LINK」等无意义占位符，导致模型无法推断跳转意图。需补充：

  • 必要描述性锚文本：<a> 内文字须描述目标（如「HelloWorld 完整样例（GitCode）」），禁止「LINK」「点击这里」；
  • 可选title：链接标签上可补充用途说明；
  • 可选站外来源标注：GitCode 等外链旁附完整域名或 external 标记。

以抓取 HelloWorld（CANN 9.0.0） 为例，文中「完整样例请参考 LINK」对向量检索和 LLM 引用而言形同无目标语义的链接。实测参见 问题论证 · 链接语义。

4. 隐藏语义 语义完全丢失

Tab 非激活面板、折叠面板等交互 UI，在默认抓取及默认 RAG 管道下属于「语义完全丢失」类型：正文虽存在于 DOM 中，但被 display: none 等 CSS 规则隐藏，而多数管道不遍历隐藏节点，导致知识库中无对应 chunk。调整策略为：

  • 必要Tab 全量可见：各面板源码完整，标签配有明确文本，渲染页正文全量可见；禁止使用 display: none 隐藏非激活项；
  • 必要折叠默认展开：标题具备语义，初始状态下面板区内正文完全展开；禁止通过 CSS 隐藏折叠内容；
  • 可选管道层扁平输出：在机器处理层将 Tab 面板及折叠内容全量展开，以 H3 标签标注各面板标题后入库。

以抓取 CANN 软件下载（CANN 9.0.0） 为例：多轴 Tab 选型与「我不知道硬件信息」折叠区内正文，默认抓取可能只入库当前激活组合或标题七字，其余安装路径与硬件确认步骤等价于未入库。实测参见 问题论证 · Tab 隐藏语义、问题论证 · 折叠面板。

5. 代码语义 语义劣化入库

代码块在默认抓取及默认 RAG 管道下属于「语义劣化入库」类型：源码逻辑虽能进入 chunk，但 highlighttable 将行号混入代码文本中。同时缺少 language-xxx 标注，导致模型拿到的代码无法直接复用，也难以区分 bash、C++、CMake 等语言类型。调整策略为：

  • 必要行号与代码分离：行号由 CSS 渲染，不写入 code 文本节点；弃用 highlighttable 表格布局承载代码；
  • 必要language-xxx 标注：pre > code 须标明语言类型（如 language-cpp、language-bash、language-cmake）；
  • 可选文件名/场景标注：代码块上方注明上下文信息（如：hello_world.asc、CMake 编译场景）；
  • 可选HTML 实体解码：管道入模前将 &quot;（双引号 "）等 HTML 实体还原为可读字符。

以抓取 HelloWorld（CANN 9.0.0） 为例：hello_world.asc 核函数代码入库后，出现了 1, 2, 3…31 行号前缀。对向量检索和 LLM 引用而言，这段代码等同于无法编译的噪声文本。具体实测参见 问题论证 · 代码语义。

6. 表格的结构语义 语义劣化入库

复杂规格表在默认抓取及默认 RAG 管道下属于「语义劣化入库」类型：表题未写入 caption、空单元格与列表伪多行会导致入库后行列从属丢失。调整策略为：

  • 必要表题 / caption：如「表1 Ascend C Add算子设计规格」须写入 <caption>，入库后可作检索锚点；
  • 必要<th> 表头：I/O 子表的 name / shape / data type / format 须用表头单元格，禁止样式伪装；
  • 必要接口列表独立化：「使用的主要接口」改为 <ul> 或合并单元格，禁止拆成伪数据行；
  • 可选机器层 Markdown 表格：为规格表额外输出 MD 副本，保留 I/O 行列与接口列表结构。

以 Add 自定义算子 · 表1 Ascend C Add算子设计规格 为实测对象：表题可见但非 caption、5 列空网格与「使用的主要接口」伪多行并存，入库后 API 列表与算子规格从属易丢失。具体诊断参见 问题论证 · 表格的结构语义。

7. 提示语义 语义劣化入库

「注意提示」在默认抓取及默认 RAG 管道下，属于「语义劣化入库」类型：notebody 正文虽能入库，但提示类型（如注意/警告/说明）仅由装饰图标传达，缺乏文本等价物，导致模型无法区分提示级别，也无法按类型进行检索过滤。此外，嵌套在步骤列表内的提示若被扁平化处理，步骤与提示之间的从属关系亦会丢失。调整策略为：

  • 必要data-admonition-type 标注：源码中标注 note / warning / tip / danger 等提示类型；
  • 必要补充文本类型前缀：渲染页中用「注意：」「警告：」等文字替代 note_3.0-zh-cn.png 装饰图标；
  • 必要机器层引用块（blockquote）：将提示转换为 Markdown 格式，如 > **注意** 正文内容，保留类型标识与正文；
  • 可选补充与步骤从属关系：对于嵌套在 <ol><li> 内的提示，抓取时保留原始层级关系，禁止扁平化处理。

以抓取 环境准备（CANN 9.0.0） 为例：set_env.sh 说明正文虽能检索，但 chunk 中缺少「注意」类型标签，导致其与普通段落难以区分。具体实测参见 问题论证 · 注意提示（Note）类型语义。

8. 信息架构与跨页语义 语义未结构化

面包屑、版本号、上下篇关系、锚点等元素在渲染页中可见，但默认管道仅抓取正文段落，未将这些信息写入 chunk 元数据——属于「语义未结构化」类型。RAG 只能进行全文相似度匹配，无法按版本过滤、无法消歧同名章节、也无法推理学习路径。调整策略为：

  • 必要定义页级身份：明确 version、doc_id、applicable_devices 等字段，回答「哪一版、适用谁」的问题；
  • 必要绑定跨页关系：保留 breadcrumb、prev/next、父主题等关系，用于消歧（如区分「环境准备」属于入门教程还是软件安装），并保留章节间的跳转逻辑；
  • 必要管道同步入库：页面上可见的版本、面包屑等信息，入库时须同步写入 chunk 的结构化字段（如 JSON-LD 或 Front Matter），不能仅有视觉可读形式而向量库中缺失；
  • 可选文章摘要：在文档头部补充 60–120 字的摘要，概括本文主题与适用读者，作为检索锚点（当前普遍缺失）。

9. 格式交付与抓取入口 语义劣化入库

当前抓取 .html 或 .md 渲染页时，抓取对象均为壳层而非机器层。壳层内容一并入库，导致核心语义被淹没。正文 chunk 与页头、页脚、全站导航等噪声内容争抢 token 配额与向量召回权重。应优先抓取 source 或 Markdown 源文件。调整策略为：

  • 必要采用双轨交付：人类渲染页与 doc_center/source/ 或 Markdown 源文件并行发布；
  • 必要澄清 .md URL 格式：.md 后缀的 URL 未必是真实 Markdown 源文件，须明确区分；
  • 必要定义机器消费规则：机器应直接抓取 doc_center/source/ 或 Markdown 源文件，而非抓取用户浏览器中带导航栏的大页面；
  • 必要增强站点发现：部署 llms.txt 文件，放行 doc_center/source/ 路径；sitemap 优先收录机器源 URL；
  • 可选增加全站索引链接：在全局模板的 <head> 中增加 <link rel="llms" href="/llms.txt">；
  • 可选增加站点 Markdown 入口：在渲染页提供「机器可读版本」链接，指向对应的 Markdown 源文件。

10. 信源时效

信源可能来自第三方或旧版本，导致版本错误或非官方内容被优先召回。调整策略见 问题论证 · 版本滞后 · 解决方案（站点版本外显、主推声明、版本过滤、溯源输出）。
