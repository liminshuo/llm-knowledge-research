模块 01 · 研究概览

研究概览

昇腾官方文档如何完整进入 RAG / 知识库——研究动机、目标与维度。

研究目标

本研究聚焦昇腾社区 Ascend C 官方文档如何进入大模型 RAG / 知识库。 这些页面原先面向人类开发者设计——依赖视觉层次、图片热区、Tab 交互与品牌化排版； 而知识库入库需要的是可检索、可引用、可跨页推理的完整文档语义，远不止正文段落。

  • 人类阅读：快速浏览、热区跳转、Tab 切换、复制代码——体验与效率优先
  • 知识库入库：正文、图意转写、热区链接、代码与表格结构、IA 元数据（版本 / 面包屑 / 上下篇）——语义尽量完整、噪声尽量剥离

同一套源文档需同时回答两个问题：人读得顺，与 机器读得全——后者是本研究的主线。

核心命题
RAG / 知识库尽量完整收录昇腾官方文档的文档语义。

研究范围

整体范围是昇腾官方文档 Ascend C 算子开发（CANN 社区版 9.0.0 编程指南）。 本研究主要聚焦下列四个典型页面——它们承载不同的组件类型与语义载体，覆盖了后续维度分析中的主要研究对象。

# 页面 组件特征
1 什么是 Ascend C 图片热区、成长地图、API 层级图
2 环境准备 注意提示、嵌套列表、代码块
3 HelloWorld 多代码块、编译分支、设备型号提示
4 Add 自定义算子开发 流程示意图、规格表格、多代码块、跨页链接、设备型号提示

研究维度

昇腾官方文档的语义不只存在于正文段落，还分布在图片、热区、链接、交互组件、代码、表格、提示框、页面元数据与版本信息等多层。默认抓取 /document/detail/ 渲染页时，大量语义无法进入 RAG，或被噪声稀释。

入库状态含义示例
完全丢失知识库里根本没有对应 chunk热区 28 条跳转、无 alt 的图意
劣化入库有文本，但结构或类型被破坏代码带行号、链接写成 LINK
未结构化页面上有，但未变成可检索元数据breadcrumb、version、设备型号

1. 图片语义（图意）

信息型图片普遍无 alt，复杂示意图无「内容转写」。以 什么是 Ascend C（CANN 9.0.0） 为例：正文区约 6 张信息型 PNG；常规转文本时图片完全不在输出里；读 HTML 只见 zh-cn_image_….png 文件名。

图片丢失的语义
API 层级架构图C API → 基础 API → 高阶 API → 算子模板库 → PyAsc 分层关系
成长地图五行学习阶段、每阶段卡片标题与意图
核心原理 / API 参考 / 算子实践卡片图卡片主题与入口意图

详见 当前问题 · 图片图意、亲和原则 · 图片（IMG-01 / IMG-02）。

2. 图片热区（Image Map）

<img usemap> + <area href> 将跳转藏在坐标里。成长地图单图含 28 个热区链接；纯文本抽取时28 个跳转关系全部丢失。解析 HTML 可抽出 href，但默认 RAG 管道通常不做，且无 alt/title 时缺少链接语义标签。

  • atlas_ascendc_map_10_0003.html（环境准备）
  • atlas_ascendc_10_10063.html（HelloWorld）
  • atlas_ascendc_10_0032.html 等算子开发入口

3. 链接语义

类型问题
热区链接坐标绑定，非正文链接（见上节）
占位符链接「完整样例请参考 LINK」——无法追溯样例仓库
面包屑 / 上下篇HTML 有，但未标准化进 chunk 元数据
全站导航（~282 个 o-link）噪声稀释正文链接语义

详见 当前问题 · 链接。

4. 交互 / UI 隐藏的语义

  • Tab 非激活面板：第二、三 Tab 正文/代码（如 bisheng vs CMake）可能缺失
  • 折叠面板：默认折叠区内步骤不可见
  • display:none：渲染层隐藏的正文片段

详见 当前问题 · 隐藏的语义（Tab）、当前问题 · 隐藏的语义（折叠面板）、亲和原则 · Tab。

5. 代码语义

  • highlighttable 行号污染（1 2 3…31 混入代码）
  • 无 language-xxx 标注，难分 bash / C++ / CMake
  • Tab 下隐藏代码、表格内嵌代码导致结构破碎

详见 当前问题 · 代码语义。

6. 表格与列表结构语义

  • 标准数据表亲和度较好；无 caption 时表格主题不明
  • highlighttable 滥用使表格语义变成代码容器
  • 嵌套列表 + 注意提示抓取后扁平化，从属关系丢失

详见 当前问题 · 表格与列表结构语义。

7. 注意提示（Note）类型语义

  • notebody 正文可入库，但提示类型（注意/警告/说明）丢失
  • 装饰图标 note_3.0-zh-cn.png 无语义
  • 无结构化 admonition-type，无法按类型检索

详见 当前问题 · 注意提示（Note）类型语义。

8. 信息架构（IA）与跨页语义

元数据作用现状
breadcrumb / 父主题消歧同名章节有 HTML，机器层未标准输出
prev / next学习顺序未作关系边入库
doc_id / Topic 锚点精确定位、切片边界存在但未标注 chunk
version（8.5 / 9.0）防版本混淆多版本并存，检索常混
applicable_devices设备适用性视觉卡片，无结构化字段

详见 跨文档结构感知、单文档结构感知。

9. 格式、交付与抓取入口

问题后果
抓渲染页（~224KB）而非 doc_center/source/（4–11KB）噪声大、结构乱
.md 后缀 ≠ Markdown误判格式亲和度
无 llms.txt 机器友好入口爬虫不知 canonical 源
JS 动态渲染（Nuxt v-if 等）静态抓取不完整

详见 交付格式（含双轨交付方案）。

10. 噪声污染

全站导航、Cookie / 法务页脚、布局 class 等无关内容入库后，稀释正文语义密度，导致 RAG 召回时正文 chunk 被导航 chunk 干扰——语义不是消失，而是被淹没。

11. 时效与信源语义

多版本并存、检索偏旧版或第三方教程、检索与生成阶段来源不一致，会导致知识库中版本错误或非官方来源优先。详见 检索阶段、生成阶段、版本滞后问题。

入库改造优先级

优先级维度
P0 图片图意 + 热区导航 + 链接（含占位符）+ Tab/折叠展开 + IA 元数据（breadcrumb、version、prev/next、doc_id）
P1 代码去行号与语言标注 + 注意提示类型 + 表格 caption + 设备适用性字段化
P2 改抓 doc_center/source + 剥离导航噪声 + llms.txt + 版本消歧
P3 关键 PNG 视觉转写 + 多模态向量索引 + Topic ID 切片边界
维度总结
完整收录文档语义，不能只抓正文段落。除图片图意、图片热区、链接外，还必须处理被 UI 藏住的内容、代码与提示的结构化类型、跨页 IA 元数据，以及抓取入口与噪声治理——在机器层把图、链、关系写成文本和元数据再入库，而非指望大模型在线「看图」或只抓渲染页正文。
